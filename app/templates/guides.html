{# ---------------------------------------------------------------- getting started #}
{% call card('Getting started') %}

Create the configuration with setup.sh (random secrets, interactive or non-interactive) and start the stack. The database schema is created and migrated automatically on every start.

{% set x %}./setup.sh # interactive ./setup.sh -y --base-url https://registry.example.com --admin-password 'S3cure-Passw0rd' docker compose up -d --build{% endset %}{{ code('g-start-1', x) }}

{# ---------------------------------------------------------------- go #}
{% call card('Go modules') %}

Florepo implements the GOPROXY protocol (list, .info, .mod, .zip, @latest). Proxy repositories cache proxy.golang.org and also relay the checksum database (sum.golang.org), so go verifies modules without direct internet access. Note: the go command never sends credentials over plain HTTP – for private Go repositories use HTTPS (see Operations → TLS) or make the repository publicly readable.

Use the cache (and the checksum database through it)

{% set x %}go env -w GOPROXY={{ scheme }}://USER:TOKEN@{{ host }}/go/{{ r.go_proxy }},direct go env -w GOSUMDB="sum.golang.org {{ scheme }}://USER:TOKEN@{{ host }}/go/{{ r.go_proxy }}/sumdb/sum.golang.org" go mod download{% endset %}{{ code('g-go-1', x) }}

Publish a private module version

Upload a zip of the module directory; Florepo checks go.mod, enforces semantic versions (and the /vN suffix for v2+) and repacks the files into the module@version/ layout. Upper-case letters in the module path are written as ! + lower-case (GOPROXY encoding).

{# ---------------------------------------------------------------- cache #}
{% call card('Proxy cache & retention') %}

Proxy repositories fetch from the upstream on first request and serve from disk afterwards. Packages/layers are immutable and kept; index metadata (pip pages, npm packuments, Docker tags, apt/dnf/apk indexes) is refreshed after PROXY_METADATA_TTL (default 300 s). If the upstream is down, the cached copy is served.

How long cached packages stay on disk

Repository settings → Keep cached packages on disk for N days after the last download. The worker removes expired entries hourly and runs a garbage collection; a removed package is simply fetched again when requested. 0 = keep forever.

{% set x %}# set retention to 30 days curl -X PATCH -H "Authorization: Bearer TOKEN" -H "Content-Type: application/json" \ -d '{"cache_retention_days": 30}' {{ base }}/api/v1/repositories/{{ r.dockerhub }} # usage and manual purge (all entries, or only those unused for N days) curl -H "Authorization: Bearer TOKEN" {{ base }}/api/v1/repositories/{{ r.dockerhub }}/cache curl -X POST -H "Authorization: Bearer TOKEN" -H "Content-Type: application/json" \ -d '{"older_than_days": 90}' {{ base }}/api/v1/repositories/{{ r.dockerhub }}/cache/purge docker compose exec web flask --app wsgi purge-cache {{ r.dockerhub }} --older-than 90{% endset %}{{ code('g-cache-1', x) }}

The cache hit rate per period is shown under Reporting → Overview; every download records whether it was a hit or a miss.

{# ---------------------------------------------------------------- quotas #}
{% call card('Quotas') %}

Repository quota (repository settings or API, e.g. 20G): hosted repositories reject uploads that would exceed it with HTTP 413 and a clear message (also docker push: layers that already exist in another repository are counted when the manifest is pushed). For proxy repositories the value is the cache size limit: the worker evicts the least recently used cached artifacts hourly down to 90 %. User quota: total size a user may upload to hosted repositories – a global default for all non-admin users (Administration → Storage & quotas) and an individual value on the user's page (custom / unlimited). Usage is the logical size of the stored artifacts; Docker layers shared by several tags count once per repository.

{% set x %}# 50 GB for a hosted repository, 200 GB cache limit for a proxy curl -X PATCH -H "Authorization: Bearer TOKEN" -H "Content-Type: application/json" -d '{"quota": "50G"}' {{ base }}/api/v1/repositories/{{ r.docker }} curl -X PATCH -H "Authorization: Bearer TOKEN" -H "Content-Type: application/json" -d '{"quota": "200G"}' {{ base }}/api/v1/repositories/{{ r.dockerhub }} # default user quota 10 GB, unlimited for one user, current usage curl -X PUT -H "Authorization: Bearer TOKEN" -H "Content-Type: application/json" -d '{"default_user_quota": "10G"}' {{ base }}/api/v1/storage/quotas curl -X PATCH -H "Authorization: Bearer TOKEN" -H "Content-Type: application/json" -d '{"quota_bytes": 0}' {{ base }}/api/v1/users/7 curl -H "Authorization: Bearer TOKEN" {{ base }}/api/v1/storage{% endset %}{{ code('g-quota-1', x) }}

{# ---------------------------------------------------------------- storage #}
{% call card('Storage: disk, NFS, S3') %}

Artifacts are stored content-addressed (identical files only once). The backend is chosen with environment variables; Administration → Storage & quotas shows it and runs a write/read/delete check. Database, signing keys and the Trivy cache always stay on the local data volume.

Local disk (default) or a network file system

STORAGE_BACKEND=fs stores blobs below STORAGE_PATH. Mount an NFS (v4.1+), SMB or CephFS share there to share it between hosts – uploads are written to a temporary file on the same file system and renamed atomically. The containers run as uid 1000, the export must allow it to write. docker-compose.nfs.yml mounts an NFS export as the storage volume:

{% set x %}# .env NFS_SERVER=10.0.0.20 NFS_EXPORT=/export/florepo COMPOSE_FILE=docker-compose.yml:docker-compose.nfs.yml # /etc/exports on the NFS server /export/florepo 10.0.0.0/24(rw,sync,no_subtree_check,all_squash,anonuid=1000,anongid=1000) # move existing data once docker compose stop web worker nginx docker run --rm -v florepo_data:/data -v florepo_storage:/nfs alpine cp -a /data/storage/. /nfs/ docker compose up -d{% endset %}{{ code('g-storage-1', x) }}

S3 compatible object storage

STORAGE_BACKEND=s3 works with AWS S3, Ceph RGW, Garage, Wasabi, SeaweedFS, MinIO, … Uploads are staged on local disk (STAGING_PATH) so their digest can be verified, then uploaded (multipart). Downloads (S3_SERVE): proxy (default) – nginx streams the object from the store, clients only talk to Florepo; redirect – clients get a pre-signed URL (they need access to the object store); stream – through the app (without nginx). docker-compose.s3-local.yml bundles SeaweedFS as a ready-to-run example.

{% set x %}# .env – e.g. AWS STORAGE_BACKEND=s3 S3_BUCKET=my-florepo S3_REGION=eu-central-1 S3_ACCESS_KEY_ID=AKIA... S3_SECRET_ACCESS_KEY=... # other providers: S3_ENDPOINT_URL=https://s3.example.com (path-style addressing is used automatically) # optional: S3_PREFIX=prod/ S3_SERVE=proxy|redirect|stream S3_CA_BUNDLE=/data/ca.pem S3_USE_PROXY=false # migrate existing file system data, then switch docker compose run --rm web flask --app wsgi storage-copy # copies blobs + SBOMs, skips existing objects docker compose up -d docker compose exec web flask --app wsgi storage-check{% endset %}{{ code('g-storage-2', x) }}

{# ---------------------------------------------------------------- security #}
{% call card('Scanning, SBOM & policies') %}

Every version is scanned on upload / first cache fill and re-scanned periodically: Trivy for images and OS packages, Trivy + OSV.dev for PyPI, npm, Maven, Go, NuGet and Cargo (Helm charts and generic files: Trivy finds embedded lock files, jars and Go/Rust binaries). Optionally ClamAV checks every file for malware (see below). Signature updates and re-scan intervals are configured under Administration → Scanner & DB.

Block vulnerable downloads

Repository setting Block downloads from severity: affected versions are rejected with HTTP 403 (and hidden from pip/npm and hosted indexes). Example: block everything with CRITICAL findings coming from Docker Hub:

{% set x %}curl -X PATCH -H "Authorization: Bearer TOKEN" -H "Content-Type: application/json" \ -d '{"block_severity": "CRITICAL"}' {{ base }}/api/v1/repositories/{{ r.dockerhub }}{% endset %}{{ code('g-sec-1', x) }}

CI gate and SBOM

{# ---------------------------------------------------------------- clamav #}
{% call card('Malware scanning (ClamAV)') %}

Optionally every new or changed version is streamed to ClamAV (clamd) before the vulnerability scan – all files of a package, for Docker images config and layers of the scanned platform (archives such as zip, wheel, jar, tar.gz and image layers are unpacked by ClamAV). Periodic re-scans repeat the check with current signatures. Infected versions are blocked (HTTP 403, hidden from indexes) and trigger an e-mail alert if alerts are enabled. Optionally new uploads of hosted repositories are held back until they were scanned. ClamAV (GPL-2.0) runs as a separate container; it needs about 1.5–3 GB RAM for the signatures, which freshclam updates automatically.

{% set x %}# .env – start the optional clamav service COMPOSE_PROFILES=clamav docker compose up -d # first start downloads the signatures (~ 1-2 minutes) # Administration → Scanner & DB → Malware scanning, or via the API: curl -X PUT -H "Authorization: Bearer TOKEN" -H "Content-Type: application/json" \ -d '{"enabled": true, "host": "clamav", "port": 3310, "block_infected": true, "block_unscanned": false, "max_file_mb": 1024}' \ {{ base }}/api/v1/clamav curl -H "Authorization: Bearer TOKEN" {{ base }}/api/v1/clamav # engine, signature version, counters # result per version: .scan.malware.status = clean | infected | error | none curl -s -H "Authorization: Bearer TOKEN" {{ base }}/api/v1/versions/42 | jq .scan.malware{% endset %}{{ code('g-clam-1', x) }}

{# ---------------------------------------------------------------- ldap #}
{% call card('LDAP / Active Directory') %}

With LDAP enabled (Administration → Authentication) users sign in with their directory credentials – in the web UI and with every client that uses HTTP Basic (docker login, pip, npm --auth-type=legacy, Maven, NuGet, Helm, …). The account is created on the first sign-in; role and write permissions come from groups: the first matching mapping row decides the role (admin, auditor, deployer, reader), deployer rows may restrict write access to repositories. Users without a mapped group are refused (or get a default role). A periodic sync disables accounts that were removed, disabled in AD or dropped from all mapped groups – their API tokens stop working at the same time. Local accounts (e.g. the bootstrap admin) keep working. API tokens are recommended for CI.

{# ---------------------------------------------------------------- performance #}
{% call card('Performance & metadata cache') %}

Large files (layers, jars, wheels, .deb/.rpm, charts, …) are streamed by nginx straight from disk or the object store. The expensive part for the application is rendering metadata – npm packuments, PyPI simple pages, maven-metadata.xml, Helm index.yaml, NuGet registrations, Cargo index files, Go version lists. These documents are cached per web worker (METADATA_CACHE_MB, default 32 MB) and stored pre-compressed with gzip. Each request checks a fingerprint of the underlying data (one index lookup), so uploads, deletions, scan results, blocks and policy changes are visible immediately; responses carry an ETag and conditional requests are answered with 304. The response header X-Florepo-Cache: hit|miss shows the effect; statistics are part of /api/v1/storage.

Measured on a development machine (Docker Desktop, 50 parallel clients): npm packument 234 → 657 req/s, PyPI simple index 286 → 689 req/s, maven-metadata.xml (proxy) 43 → 602 req/s, a 6 MB Helm index 28 → 200 req/s – with 5–10× less data transferred. For more throughput: more web workers (WEB_WORKERS), more web containers (stateless with S3 or a shared NFS storage) and a PostgreSQL server close to the application.

{% set x %}curl -s -o /dev/null -D - -H "Accept-Encoding: gzip" -u USER:TOKEN {{ base }}/npm/{{ r.npm_proxy }}/lodash | grep -i "x-florepo-cache\|etag\|content-encoding" # .env METADATA_CACHE_MB=64 # per web worker process, 0 = off WEB_WORKERS=16{% endset %}{{ code('g-perf-1', x) }}

{# ---------------------------------------------------------------- ops #}
{% call card('Operations, upgrades & migrations') %}

Upgrading – database migrations run automatically

The schema is versioned with Alembic. When a new version starts, the web container applies all pending migrations (0001 → 0002 → …) before it accepts requests; a database lock prevents concurrent migrations and the worker waits until the schema is current. Installations created before migrations existed are detected and stamped automatically.

{% set x %}git pull # or a new image tag docker compose up -d --build # migrates automatically, see: docker compose logs web | grep migrat docker compose exec web flask --app wsgi db-current # current: 0002 head: 0002{% endset %}{{ code('g-ops-1', x) }}

For developers: adding a migration

{% set x %}# 1. change app/models.py 2. generate the migration (review it!) 3. commit it flask --app wsgi db-revision -m "add column foo to repository" flask --app wsgi db-revision -m "backfill foo" --empty # data migration (write op.execute(...) yourself) pytest tests/test_migrations.py # fails if models and migrations differ{% endset %}{{ code('g-ops-2', x) }}

More scan workers

Scans are distributed over all workers (each runs one Trivy scan at a time); one worker is elected leader via a database lock and runs DB updates, re-scan scheduling, alerts and cache retention. If it stops, another worker takes over within seconds. Measured: 3 workers re-scanned ~260 versions 2.7× faster than one. Administration → Scanner & DB lists all running workers.

{% set x %}# .env WORKER_REPLICAS=4 docker compose up -d # or ad hoc: docker compose up -d --scale worker=4{% endset %}{{ code('g-ops-5', x) }}
